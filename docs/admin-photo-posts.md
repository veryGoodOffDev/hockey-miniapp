# Посты от лица бота: фотографии и альбомы

В «Админ → Напоминания» можно выбрать до 10 изображений одновременно или добавлять по нескольку. Вставка из буфера также поддерживается. Каждое фото можно удалить из предпросмотра. Одна общая подпись до 1024 символов; без фото текст до 3500. Одна фотография отправляется через sendPhoto, от двух до десяти — одним Telegram-альбомом через sendMediaGroup. Подпись прикрепляется к первой фотографии.

## Исправление загрузки

Раньше исходный файл отправлялся целиком (до 10 МБ), поэтому мог не пройти обычный лимит nginx 1 МБ. Это воспроизведено в локальном HTTP-тесте, но не подтверждено как единственная причина конкретного production-сбоя. Ошибка Telegram или прокси скрывалась общим текстом.

Теперь браузер последовательно подготавливает фотографии: JPEG, длинная сторона до 1920 px, файл до 850 КиБ, небольшие отдельные миниатюры. Изначальный файл до 30 МБ; формат должен декодироваться браузером (для неподдерживаемого HEIC предлагается JPEG/PNG). Прозрачность заполняется белым. Сервер получает **каждую** картинку отдельным multipart-запросом менее 1 МБ, а затем короткий JSON-запрос публикует все картинки альбомом. Даже десять фотографий не требуют большого входящего HTTP-запроса. Увеличивать лимит nginx до размера всего альбома не требуется, если существующий лимит не меньше 1 МБ.

Новые ошибки различают 413 от прокси, отсутствие нового endpoint после неполного деплоя, запрет Telegram отправлять фото, недопустимый формат, истёкшие загрузки и потерю подтверждения. До подтверждённой отправки черновик и фотографии остаются в редакторе.

## API и хранение

- `POST /api/admin/bot-messages/photos`: multipart поле photo, подготовленный JPEG/PNG/WEBP до 900 КиБ. Возвращает временный непрозрачный token.
- `POST /api/admin/bot-messages/send`: JSON `{text, photo_tokens: [...], request_id}`. Старый текстовый JSON и multipart с одним полем photo сохранены для совместимости. Новые фотографии отправляются только через предварительную загрузку.
- Оба маршрута сохраняют существующую авторизацию и доступ **только super-admin**; файлы принимаются после проверки прав. Сервер проверяет сигнатуру файла, размер, число фото и принадлежность токенов пользователю.
- Файлы временно находятся в памяти одного backend-процесса до 10 минут: общий предел 50 МиБ, до 20 файлов на администратора. После успешной публикации буферы удаляются; истёкшие файлы очищаются таймером. После рестарта потребуется загрузить их заново. Нужен один backend-инстанс, как и для текущего PvP.
- request_id защищает от повторной публикации идентичного запроса в текущем процессе в течение 15 минут, включая одновременные запросы и потерю HTTP-ответа после успешной публикации. Изменение тела под тем же идентификатором запрещено. При неоднозначной сетевой ошибке Telegram повторная отправка автоматически не запускается; сначала проверить чат. Защита не переносится через рестарт процесса.
- Для каждого сообщения альбома сохраняются отдельный message_id, media_group_id, индекс и число фото в существующем bot_messages.meta. В истории видно «Альбом · фото N/M»; удаление/синхронизация действуют на выбранную фотографию. Ошибка записи истории после доставки не выдаётся за отказ отправки.

## Деплой и проверка

Деплоить **backend, затем frontend**. Новых зависимостей, секретов или миграций нет. Новый endpoint photos должен проксироваться вместе с существующим /api/. При 404 обновить backend/проверить маршрут прокси. При 413 проверить фактический лимит тела (достаточно 1 МБ на запрос). Production nginx и права конкретного бота из этой среды не проверялись; в реальный командный чат тестовые сообщения не отправлялись.

`node --test backend/src/customBotPost.test.js backend/src/customPostUpload.test.js` проверяет создание альбома, подпись, лимит десяти фото, временные токены, изоляцию пользователей, истечение срока и идемпотентность. HTTP-тест проходит реальные multer и grammY с локальным макетом Telegram API, воспроизводит отказ 413 для исходного фото >1 МБ и успешный альбом через подготовленные загрузки. Также проверяет CHAT_SEND_PHOTOS_FORBIDDEN, отказ истории и потерю ответа без слепого повтора.

Frontend: `npm --prefix webapp run build`. Браузерная проверка включает несколько больших PNG, реальную подготовку JPEG, предпросмотр, отдельные загрузки, общую подпись, сохранение черновика при отказе Telegram и повтор без лишней загрузки. После деплоя выбрать 2–3 фото, добавить подпись, отправить и проверить один альбом в Telegram. Если Telegram запрещает отправку фото, разрешить её боту в настройках командного чата.

## Почему мог зависать вход

Найден подтверждённый недостаток кода: запрос /api/me не имел конечного срока ожидания, а проверка членства Telegram могла долго ждать Telegram API. Браузерный вход по bearer не проходит ту же проверку членства. Это возможная причина различия, но точная причина на конкретном телефоне не установлена без сетевых данных/production-логов.

Теперь вход ограничивает каждую попытку HTTP двенадцатью секундами, существующие резервные адреса сохраняются. Остальные JSON-запросы обычно ограничены двадцатью секундами, загрузка файла — сорока пятью; публикация поста с ожиданием Telegram — девяноста. Ограничение действует и на чтение тела ответа. При таймауте мутации не повторяются автоматически на другом адресе. Вход отображает ошибку и «Повторить», предыдущая попытка отменяется при повторе/закрытии экрана. Backend ограничивает getChatMember восемью секундами; таймаут возвращает telegram_unavailable без обхода проверки доступа.

После деплоя открыть приложение заново в Telegram на телефоне. Если войти всё ещё нельзя, сохранить текст появившейся ошибки и сверить backend-лог /api/me, CORS, доступность публичного API и проверку членства; бесконечный загрузчик больше не должен скрывать отсутствие ответа сервера.

Проверки: `npm --prefix webapp run build`, `node --test webapp/src/fetchApiResponse.test.js`, `RSVP_TEST_DATABASE_URL=postgresql://postgres@localhost:5432/hockey_rsvp_checks npm --prefix backend test`. Браузерная проверка использует имитацию Telegram-контекста и контролируемые ответы API, не отправляет сообщений в реальный чат.
