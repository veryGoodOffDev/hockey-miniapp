# Ответы и реакции от имени бота

В «Админ → Напоминания» главному администратору доступен блок «Сообщения чата».

1. Нажать «Загрузить сообщения чата». Показываются последние 20 сообщений назначенной через `/setchat` группы. Более ранние загружаются отдельной кнопкой, новые — через «Обновить сообщения чата».
2. Нажать «Ответить» у нужного сообщения. В редакторе видны автор и фрагмент исходного сообщения. Отправить текст, фото или альбом через существующий механизм загрузки. Ответ публикуется ботом с Telegram reply. Если исходное сообщение удалено, ответ отдельным постом не отправляется; черновик сохраняется и можно выбрать другую цель.
3. Нажать «Выбрать реакцию»: раскрывается прокручиваемый блок всех разрешённых группе реакций. Список читается через getChat.available_reactions и проверяется сервером при отправке. Если поле отсутствует, используются все обычные реакции из каталога Bot API; пустой массив означает запрет реакций. Кастомные эмодзи отправляются по custom_emoji_id и показаны базовым эмодзи с отметкой ✦ (без оригинальной анимации; при недоступности метаданных — ⭐ и ID в подсказке). Платные реакции ботам недоступны. Выбор заменяет предыдущую реакцию бота; повторное нажатие выбранной или «Убрать реакцию» снимает её. Настройки кэшируются на минуту, без запросов на каждое сообщение; Telegram может отклонить реакцию на конкретное сообщение.

## Backend и хранение

- `chatInbox.js` содержит преобразование Telegram-сообщений, SQL-репозиторий, middleware записи и API реакций/списка.
- Middleware подключается в `createBot` до команд и обработчиков профиля; запись выполняется и для `message`, и для `edited_message`. Ошибка архива не блокирует существующие команды бота.
- Сохраняются только сообщения текущей `notify_chat_id` с типом group/supergroup. Личные сообщения, посторонние группы и служебные события не попадают в список.
- Таблица `chat_inbox_messages` и добавленные поля `deleted_at`, `deletion_reason` создаются/мигрируются автоматически существующим `ensureSchema` при старте backend. Ключ `(chat_id, message_id)` защищает от дубликатов; старый update не перетирает более новое редактирование. Запись редактирования сохраняет установленную реакцию.
- Хранятся имя/username автора, текст/подпись, тип вложения, время, ссылка на исходное сообщение по ID и собственная реакция бота. Сами вложения не скачиваются. В этой версии фото/стикеры/видео входящих сообщений показаны как тип вложения и подпись, без превью.
- В списке доступны сообщения за 30 дней. Физическая очистка старых записей запускается входящим сообщением не чаще раза в час; при отсутствии трафика строки могут оставаться в БД, но API их не выдаёт.
- Сообщения, отправленные самим ботом, по-прежнему находятся в отдельной истории постов, не во входящем списке.
- Telegram не предоставляет историю чата или обычные события удаления. Список заполняется новыми сообщениями после подключения функции. Мгновенно обнаружить удаление невозможно: после явного подтверждения Telegram при попытке реакции или ответа (например MESSAGE_ID_INVALID или message to be replied not found) сервер сохраняет deleted_at/deletion_reason. Текст остаётся в списке с пометкой «Удалено из чата», оба действия блокируются в UI и на backend (410 message_deleted), последующие попытки не вызывают Telegram. Обычный запрет реакции, ошибка прав и сетевой сбой не считаются удалением. До первого подтверждения сообщение может выглядеть обычным; никаких скрытых тестовых публикаций или изменения реакций для проверки существования нет. Отложенный update редактирования не снимает пометку удаления; черновик ответа сохраняется и может быть отправлен другому сообщению. При старте сохранено существующее поведение polling `drop_pending_updates: true`; офлайн-период не является гарантированным архивом.
- Изменение реакции через админку сохраняется в БД; ручные изменения от имени бота другими инструментами не синхронизируются.

## API

Все маршруты используют существующую авторизацию Mini App / web session, проверку членства группы и super-admin. Клиент не задаёт `chat_id` или отправителя.

- `GET /api/admin/chat-messages?before=<message_id>` — до 20 сообщений, включая deleted_at/deletion_reason, `has_more`, объекты `reactions` (type/key/label/emoji или custom_emoji_id), `reactions_error`, совместимый `reaction_choices` обычных emoji.
- `POST /api/admin/chat-messages/:messageId/reaction` принимает `{ "reaction": { "type": "emoji", "emoji": "👍" } }`, `{ "reaction": { "type": "custom_emoji", "custom_emoji_id": "123" } }` или `{ "reaction": null }` для снятия. Старый `{ "emoji": "👍" }` / `""` поддерживается. Сервер проверяет ID, наличие и отсутствие пометки удаления в текущем чате, а также выбранную реакцию в настройках группы. В bot_reaction обычные эмодзи хранятся без variation selector FE0F, кастомные — как custom:<id>. Telegram timeout — 10 секунд; одновременное изменение одной реакции получает `reaction_busy`.
- `POST /api/admin/bot-messages/send` дополнительно принимает `reply_to_message_id`. Сервер ищет цель в текущем чате, передаёт `reply_parameters` с `allow_sending_without_reply: false`. Цель входит в отпечаток идемпотентного запроса, поэтому смена цели не переиспользует результат другого ответа. В истории каждого отправленного сообщения сохраняется `meta.reply_to_message_id`.

## Деплой

Сначала backend (он автоматически добавляет поля удаления в существующую таблицу), затем frontend. Новых npm-зависимостей, env-переменных, WebSocket или изменений nginx не требуется. Бот уже администратор группы; Privacy Mode не препятствует получению обычных сообщений администратором. Не запускать второй процесс polling с тем же токеном.

После деплоя:

1. Переоткрыть Mini App.
2. Отправить обычное новое сообщение в назначенную группу с аккаунта участника.
3. Загрузить сообщения в админке, ответить на него текстом, затем проверить фото/альбом.
4. Поставить реакцию, заменить её и убрать, сверяя результат в Telegram.
5. При отказе проверить права бота и разрешённые реакции группы. Сообщения других ботов Telegram этому боту не передаёт.

## Проверки

`node --test backend/src/chatInbox.test.js backend/src/chatReactions.test.js backend/src/customBotPost.test.js backend/src/customPostUpload.test.js`

SQL-проверка использует только отдельную локальную базу с суффиксом `_checks`:

`RSVP_TEST_DATABASE_URL=postgresql://postgres@localhost:5432/hockey_rsvp_checks npm --prefix backend test`

`npm --prefix webapp run build`

Проверены middleware настоящего grammY, отправка ответов и реакций через локальный HTTP-макет Telegram API, изоляция чатов, ошибки, повторная отправка без дубля, хранение/редактирование/пагинация/очистка в PostgreSQL. В Chromium проверены интерфейс, ошибки реакций и удалённой цели, сохранение черновика, смена цели, пагинация и ширина 320/390/430 px. Реальные сообщения и реакции в командную группу во время разработки не отправлялись.

Дополнительно проверены: полный/ограниченный/выключенный каталог группы, кастомные реакции, исключение платных реакций, кэш/ошибки getChat, различение удаления и запретов Telegram, сохранение пометки при позднем update, запрет повторных reply/reaction без вызова Telegram, сохранение черновика и раскрывающийся выбор в Chromium.
