# Заходы в приложение и посещаемость игр

## Исправление календаря вовлечённости

В `/api/admin/engagement` параметры `year` и `month` ранее обрабатывались функцией `int()`, предназначенной для навыков игроков: она ограничивает результат значениями 1–10. Поэтому ноябрь (11) и декабрь (12) превращались в октябрь (10), а год всегда становился 10 и заменялся текущим годом. Frontend показывал календарь ноября, но получал октябрьские ключи дат: отсюда ложные нули. Просмотр исторических лет тоже работал неправильно.

`analyticsPeriods.js` разбирает календарные параметры отдельно: год 2000–2200, месяц 1–12. Функция навыков не менялась. Данные `app_daily_visits` не переписываются, новые посещения продолжают учитываться существующим middleware. Исправлена выборка существующих записей; никакого восстановления вымышленной истории или backfill по `last_seen_at` не выполняется.

Обработчик календаря выделен в `engagement.js`, сохраняет прежнюю авторизацию администратора и формат ответа. Ошибка БД возвращает контролируемый 503. Ответы не кэшируются. Frontend проверяет соответствие периода, защищается от запоздалых ответов, при переходе к другому месяцу выбирает день этого месяца. Кнопка «Сегодня» возвращает также нужные месяц и год. Ошибки загрузки и будущие дни показываются как «—», а не как подтверждённый ноль.

## Новый раздел «Статистика → Посещаемость игр»

Существующая статистика отдельных игроков сохранена во вкладке «По игрокам».

Новая вкладка по умолчанию открывает текущий календарный год по Москве. Доступны переключение года, возврат к текущему году, произвольные даты включительно и обновление. Диапазон ограничен 3660 днями. Группировка — по неделям (понедельник–воскресенье) или календарным месяцам. Переключение группировки выполняется локально без повторной загрузки.

- Для каждой завершённой игры считается количество RSVP со статусом `yes` («Буду»), включая гостей и ныне отключённых игроков. Это количество по имеющимся отметкам, не отдельная система фиксации фактического прихода.
- Учитываются неотменённые игры через два часа после начала — тот же порог завершения, что в UI. Текущие и будущие игры исключаются.
- График показывает **среднее на одну игру**, а не сумму игроков за неделю/месяц. Например, две игры с 10 и 30 отметками дают 20, а не 40. В статистике периода доступны число игр, сумма участий, минимум и максимум.
- Период без игр — `null` и разрыв линии. Реальная игра с нулём отметок — 0. Будущие месяцы не создают искусственного падения до нуля.
- Нажатие на график или выбор периода раскрывает конкретные игры, их даты, арену и количество игроков. Нажатие на игру открывает её карточку. Список периода и кнопки предыдущего/следующего периода доступны с клавиатуры.
- Блок сезонов показывает взвешенное по играм среднее в пределах выбранных дат: зима — январь/февраль/декабрь этого диапазона, весна — март–май, лето — июнь–август, осень — сентябрь–ноябрь. Неполный текущий сезон учитывает только состоявшиеся игры.
- Ошибка API не заменяется пустым графиком с нулевыми значениями. Есть сообщение и повторная загрузка; старые запросы отменяются при переключении диапазона/года.

Отрисовка — адаптивный SVG без новых chart-зависимостей. Состояние загрузки/ошибки, оси, выбранный период и таблица игр работают на мобильной ширине. При отсутствии ResizeObserver используется обработчик resize.

## API

`GET /api/stats/game-attendance?year=2026` или `?from=2026-01-01&to=2026-03-31`.

Требует существующей авторизации Mini App/web session и членства в группе; администратор использует существующий обход проверки членства. Отмена функций чата/комментариев на статистику не влияет.

Ответ: `ok`, `filter: {from,to,year?}`, `games: [{id,starts_at,date,location,players}]`, `years`, `as_of`. `date` и границы диапазона вычисляются в Europe/Moscow, неделя/месяц группируются по этой дате. Список имён игроков не отдаётся. Несуществующие даты, дробный год, инвертированный диапазон и диапазон больше лимита отклоняются с 400. Сбой БД — 503 `stats_unavailable`.

Используются существующие `games` и `rsvps`; нет фильтра по текущему `players.disabled` и нет JOIN, теряющего гостей. Числа соответствуют текущим отметкам игры: последующее изменение отметки администратором отразится после обновления графика. Отдельные неизменяемые снимки исторической посещаемости не создаются.

## Деплой

**Сначала backend, затем frontend.** Новых env, npm-зависимостей, таблиц и миграций нет. Старые записи заходов читать заново; вручную менять даты или пересоздавать статистику не нужно. До обновления backend новая вкладка графика будет недоступна, а frontend обнаружит неверный месяц старого обработчика.

## Проверки

```sh
node --check backend/src/index.js
node --test backend/src/analyticsPeriods.test.js webapp/src/gameAttendanceData.test.js
ANALYTICS_TEST_DATABASE_URL=postgresql://postgres@localhost:55432/hockey_analytics_checks node --test backend/src/analytics.pg.test.js
npm --prefix webapp run build
NODE_PATH=/path/to/playwright/node_modules node webapp/tests/attendance-analytics.browser.cjs http://localhost:4174/
```

PostgreSQL-тест разрешён только для localhost/127.0.0.1 и БД с суффиксом `_checks`; создаёт и удаляет отдельную временную схему. Проверяет реальные HTTP-обработчики, ноябрь, декабрь, исторический год, права, московскую границу года/дня, гостей, нулевые игры, отменённые/текущие/будущие игры и фильтр дат. Модульные тесты проверяют все 12 месяцев в нескольких годах, високосные дни, границы недели и корректный знаменатель среднего.

Браузерный тест использует только API-макеты, проверяет 320/390/430/900 px, текущий год, группировку, диапазон, отсутствие данных, запоздалый ответ, отказ и повтор, старую статистику игроков, календарь ноября, переход месяца и ошибки календаря. Реальные сообщения в Telegram не отправляются, production БД не изменяется.
