# Публикация составов: таблица или две джерси

В разделе «Составы» админ выбирает формат перед существующей кнопкой «Изменить/отправить составы в чат»:

- `columns`: одно текстовое сообщение с двумя колонками. Это формат по умолчанию, совместимый с прежним frontend и уже опубликованными таблицами.
- `jerseys`: два отдельных сообщения с фото — белая команда, затем синяя. В подписи каждого дата/время/место, группы вратарей/защитников/нападающих и имена с номерами. В каждом сообщении прежняя кнопка «Открыть составы».

Форматы независимы: можно опубликовать оба для одной игры. Имеющиеся сообщения каждого формата обновляются; другие варианты не удаляются автоматически. Это позволяет сравнить оформление и при желании вручную удалить ненужный вариант.

## Таблица

Группы G/D/F формируются одновременно для двух команд. Число строк каждой позиции равно максимуму её размеров в командах (минимум одна строка); недостающие места заполняются `—`. Поэтому заголовки нападающих не съезжают при разном числе защитников. Колонки по 16 условных моноширинных ячеек с промежутком 2. Длинное имя сокращается с многоточием, номер джерси сохраняется. HTML экранируется, переводы строк внутри имён нормализуются. Ширина emoji учитывается приближённо: Telegram и настройки крупного шрифта могут всё равно переносить длинные строки. Фотографии с отдельными списками устраняют зависимость от двухколоночного выравнивания.

## API и хранение

Существующий `POST /api/admin/teams/send` принимает `format: "columns" | "jerseys"` вместе с `game_id` и прежним `force`. Без format — columns. Существующие авторизация Telegram/web, проверка членства и админских прав сохранены. Неадминам выбор и публикация недоступны. Сервер по-прежнему проверяет устаревшие составы; HTTP 409 `teams_stale` требует отдельного подтверждения и `force:true`. Frontend сохраняет выбранный формат при повторе и корректно обрабатывает HTTP-ошибку, а не только JSON `ok:false`.

Ответ содержит `message_id` (для совместимости), `message_ids`, `format`, массив `messages` с частью и действием (`sent`, `edited`, `unchanged`), `edited` и прежние stale/removed/added. При частичной ошибке в ответе есть `partial_messages` с известными успешно обработанными частями.

Используется существующая `bot_messages`, `kind='teams'`. В JSON `meta` сохраняются `game_id`, `teams_format`, `teams_part` (`table`, `white`, `blue`), `content_key`, `changed`, `media_type`, `photo_url` и полученный Telegram `media_file_id`. Старые записи без format/part трактуются как columns/table и редактируются на месте. Для каждой пары формата/части используется последняя активная запись этой игры в текущем командном чате. Переключение чата не переносит сообщения из старого чата.

Новых таблиц и миграций нет. Для подписи фото используется `editMessageCaption`, для таблицы `editMessageText`. Существующий админский просмотр/удаление bot_messages и проверка фотографий используют прежний `meta.media_type='photo'`.

## Автоматическое обновление и повторы

Все прежние вызовы синхронизации после IN/OUT, позиции, гостя и ручного переноса между командами теперь обращаются к единому сервису. Добавлена синхронизация после повторного формирования команд. Чисто визуальная перестановка на поле внутри одной команды не меняет текстовый состав.

При переносе игрока обновляются подписи обеих затронутых команд; таблица также обновится, если была опубликована. Хэш содержания позволяет пропускать неизменившиеся сообщения при автоматической синхронизации. На изменённых публикациях появляется короткое «Составы изменены после публикации». Повтор той же публикации сам по себе эту отметку не добавляет.

Автоматическая синхронизация только редактирует уже опубликованные сообщения. Она не создаёт публикацию игры, не досылает отсутствующий вариант и не восстанавливает сообщения, удалённые вручную. При обнаружении отсутствующего сообщения запись помечается удалённой. Явная отправка выбранного формата проверяет существующие сообщения и восстанавливает недостающую часть. Ошибка `message is not modified` считается успехом; запрет редактирования не вызывает автоматического дублирования, интерфейс предлагает удалить устаревший пост и повторить отправку.

Операции одного game_id проходят последовательную очередь, которая очищается после успеха/ошибки. Контекст читается внутри очереди, чтобы поздняя операция использовала текущие составы. Известные успешные части сохраняются сразу: после сбоя второго фото повтор проверит первое и отправит только недостающее. Данные переживают перезапуск backend; очередь рассчитана на **один процесс backend**, как текущая конфигурация. Для нескольких инстансов потребуется общий механизм блокировки.

Telegram не предоставляет idempotency key для отправки сообщений. Если соединение пропало после фактической отправки, но до получения номера сообщения или записи в БД, результат может быть неизвестен; в таком случае стоит проверить чат перед повтором. Это ограничение API не устраняется локальной очередью.

## Ограничения Telegram

Перед ручной публикацией проверяются обе подписи, до первого запроса sendPhoto. Предел — 1024 символа после HTML-разметки; имена в фотографиях не обрезаются. Если команда не помещается, API возвращает `teams_caption_too_long`, frontend предлагает формат таблицы. Для таблицы проверяется лимит 4096. При автоматическом обновлении ошибка одной команды/формата не мешает попытке обновить остальные; ошибка логируется и подпись сверх лимита не отправляется.

## Картинки и деплой

Используются пользовательские файлы:

- `webapp/public/jersey-white.jpg` — 800×667, около 52 КБ.
- `webapp/public/jersey-blue.jpg` — 800×731, около 53 КБ.

Backend формирует публичные URL `/jersey-white.jpg` и `/jersey-blue.jpg` относительно существующего `PUBLIC_WEBAPP_URL`, либо `WEB_APP_URL`. Домен должен вести на frontend и отдавать JPG без авторизации. Новые env не обязательны; проверить существующий адрес. Telegram загружает фото по URL, последующие изменения подписи не перезагружают картинку. Кнопка использует `BOT_USERNAME` либо уже полученный при `bot.init()` username.

Деплой: **backend, затем frontend** стандартным `npm run build`; пользоваться фотоформатом после завершения обоих деплоев, когда новые JPG доступны. Проверить оба URL в браузере. Старый frontend продолжит отправлять columns на новом backend. Новый frontend с прежним backend не поддерживает фотоформат, поэтому backend обновить первым. Nginx/WebSocket и БД менять не нужно.

## Проверки

```bash
node --test backend/src/teamPosts/format.test.js backend/src/teamPosts/service.test.js
RSVP_TEST_DATABASE_URL=postgresql://postgres@localhost:5432/hockey_team_posts_checks node --test backend/src/teamPosts/repository.pg.test.js
node --check backend/src/index.js
npm --prefix webapp run build
# На production preview:
NODE_PATH=/path/to/playwright/node_modules node webapp/tests/team-post-formats.browser.cjs http://localhost:4174/
```

PostgreSQL-тест допускает только localhost и БД с суффиксом `_checks`, создаёт и удаляет отдельную схему. Проверяются реальный старый формат bot_messages, JSON-meta новых публикаций, сохранение после перезапуска сервиса, позиции на игру, IN/OUT и независимость игры/чата. Тесты сервиса проверяют публикации/переносы, частичную ошибку и повтор, гонки, удаление, not-modified/uneditable, пустые составы, ограничения длины и очистку очереди. Браузерная проверка использует имитацию API: оба формата, server-side stale/force, обратную связь, JPEG-файлы, ширины 320/390/430 и отсутствие админских кнопок у участника. В production и настоящие чаты тесты сообщений не отправляют.

Для ручной проверки после деплоя: опубликовать таблицу, затем фотоформат; поменять одного игрока между командами и проверить те же три message_id, обновлённые списки и ровные заголовки позиций. Повторить публикацию без правок — новых сообщений не должно появиться. Удалить одну фотографию и явно опубликовать фотоформат снова — восстановится только недостающая команда.
