# Продолжительность игры

`games.duration_minutes` — целое число минут от 1 до 1440. Значение по умолчанию — **75 минут (1 ч 15 мин)**. Время окончания: `starts_at + duration_minutes`.

## Миграция и существующие игры

`ensureSchema()` вызывает `ensureGameDurationSchema()` из `backend/src/gameDuration.js`. При первом запуске добавляется `INTEGER NOT NULL DEFAULT 75`: все существующие игры, включая исторические и уже созданные будущие, получают 75. Новые записи без явной длительности также получают 75 на уровне БД.

При повторном запуске значения не перезаписываются. Ремонтируются только NULL (на случай частичной старой схемы), сохраняется DEFAULT 75, добавляется CHECK 1–1440. Ранее выданные награды и даты игр не меняются. Время старых игр не сдвигается: меняется только вычисляемый момент окончания.

## Настройки и API

- Продолжительность видна только в админских формах создания/редактирования игры. Публичные карточки, списки и сообщения бота её не показывают.
- В настройках игры: «Продолжительность игры, мин», например 75, с подсказкой «1 ч 15 мин». Сохраняется общей кнопкой «Сохранить игру».
- Создание через плюс, одиночная игра и серия в «Админ → Игры» начинают с 75. При создании серии явно выбранное значение применяется ко всей серии. Автоматическое создание по шаблону использует DEFAULT 75.
- `POST /api/games` принимает необязательный числовой `duration_minutes`, без него — 75. `PATCH /api/games/:id` меняет поле только при явной передаче; посторонние PATCH его не сбрасывают. Строки, null, дроби, 0 и значения больше 1440 отклоняются с 400 `bad_duration_minutes`. Существующая проверка администратора сохранена.
- `GET /api/games` и `/api/game` возвращают поле вместе с прежними данными игры; frontend использует его для вычислений, не добавляя публичную подпись длительности.

## Завершение

Например, старт в 07:45 и 75 минут означают окончание в 09:00. В сам момент окончания «Идёт» меняется на «Прошла», следующая незавершённая игра получает метку ближайшей, администратору открывается награда. Локальный таймер учитывает начало/окончание и возвращение приложения из фона, независимо от опросов чата/комментариев. Скрытая вкладка догоняет время при фокусе. Архив на главном экране по-прежнему отделяется по полуночи, а не сразу после финального свистка. В админском списке завершённые игры относятся к прошедшим по фактическому окончанию.

Это вычисляемая фаза игры. Существующее поле `status` (`scheduled`/`cancelled`) не переписывается фоновой задачей в новый enum: прежняя архитектура списков и отмены сохраняется.

Общий SQL `gameEndSql()` применяется к:

- авто-проверке количества предстоящих игр и её счётчику в админке;
- статистике посещаемости игр, включая список доступных лет;
- определению прошлого держателя овечки и общего держателя трофея;
- обоим автоматическим путям послеигровых сообщений (раньше использовали разные 2/3 часа).

Настройки включения автоматических сообщений и автосоздания сохраняются. Ручная явная отправка сообщения остаётся ручным действием. Порог окончания в UI также использован для доступности награды, закрытия UI отметок после игры, подсказки джерси и напоминания держателю овечки. Существующее серверное правило закрытия обычного RSVP после начала игры не расширяется этим изменением. Голосование и Air Hockey не меняются.

## Награда на сервере

`matchAward.js` сохраняет прежние права администратора, блокирует строку игры внутри транзакции и проверяет окончание по часам PostgreSQL. До окончания: 409 `game_not_finished`, отменённая игра: 409 `game_cancelled`, неизвестная игра: 404. Работают назначение, переназначение и снятие через `best_player_tg_id: null`; остаётся одно поле победителя на матч. Гости поддерживаются, отключённые/отсутствующие игроки отклоняются.

Если после выдачи награды администратор увеличил продолжительность так, что игра снова идёт, существующая награда автоматически не удаляется. Выдача/переназначение/снятие вновь доступны после нового окончания. Повторная миграция настройки не сбрасывает.

## Деплой

1. Обновить **backend**. Миграция выполнится автоматически до запуска обработчиков/воркеров; существующие записи получат 75.
2. Обновить **frontend** и переоткрыть Mini App.

Новых env, npm-зависимостей и ручных SQL-команд не нужно. Пользователю на старом frontend может временно показываться прежний двухчасовой порог до обновления страницы, поэтому нужны обе части деплоя.

```sh
node --check backend/src/index.js
node --test backend/src/gameDuration.test.js

npm --prefix webapp run build
NODE_PATH=/path/to/playwright/node_modules node webapp/tests/game-duration.browser.cjs http://localhost:4174/
```

PostgreSQL-тесты используют только локальную БД с суффиксом `_checks` и отдельные схемы. Проверяют заполнение старых игр, DEFAULT новых, ограничения, повторную миграцию, границу выдачи, изменение продолжительности, гостей, переназначение/снятие, параллельные выдачи, статистику, прошлого держателя и автопополнение расписания.

Браузерный тест с часами и API-макетом проверяет переходы 07:45→09:00 и 07:45→09:15 без перезагрузки, награду, сохранение, создание, приватность поля для админа и 320/390/430 px. Production БД и реальные награды/сообщения в Telegram при разработке не меняются.
